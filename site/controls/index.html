TRANSLATION GUIDE

Control code reference

Control codes insert names and numbers, control page layout, or trigger game behavior. Translate the surrounding words and keep the controls required by the entry.

Reading a code

In <cF0:03>, cF0 identifies the operation and 03 is its parameter. Parameters are hexadecimal bytes: 0A is ten, for example. XX below is a placeholder for the entry’s existing value; do not type XX into a translation.

The same code can behave differently depending on how the game reads the text. An address such as 14:$541F starts with the bank number. The editor selects the appropriate rules from the entry’s bank and rendering path. Keep the exact spelling and parameter shown in that entry.

Examples explain meaning, not permission to add a code. The editors preserve the reviewed sequence of controls. Some effects are only partly understood; those entries say Not fully mapped.

Breaks and pages

CodeWhat it doesEditing guidance
<br>Starts a new line.Hello.<br>Come in. places “Come in.” on the next line. Prose and descriptions allow line-break edits; structured dialogue and queued messages retain their explicit layout.
<brk>Starts a new page/window. Whether the game waits for input depends on the calling code and the other controls.In an ordinary prose draft, Hello.<brk>Come in. requests a page break. The prose wrapper supplies the associated close controls. Other workbenches retain the existing page boundaries.
<end>Sets the message wait/end flag. It does not itself split a line and is distinct from the stored string’s terminator.The prose wrapper places this code; do not type it into an ordinary prose draft. Keep it as required in explicit-layout entries. Adding one at the end of dialogue can repeat the final box; resuming text after it without a page boundary can hide text.

A literal Enter/newline in a TSV field is not a game line break. Use the editor’s supported tokens or insertion buttons.

Names, numbers and shared text

CodeWhat it doesExample or context
<name>Inserts the player’s entered name.Hello, <name>! could display “Hello, Shiren!” The current name-entry system accepts up to six glyphs, which the editor reserves in its measurements.
<var>Inserts a name supplied by the message queue, such as a monster or character.In <var> hit <var>, the two occurrences can consume different actors in order. Preserve their roles and order when translating; they are not two copies of one fixed name.
<cE3>
<cE3:XX>		Inserts an item name or item-related text. The message path can include a count prefix.Gameplay messages use <cE3>, as in Consumed the <cE3>. Banks 11/14 dialogue use a selector inside the token, for example <cE3:09>. Keep that selector; it is not printable text.
<cE4>Inserts a runtime number, such as a level or damage value. This numeric formatter can produce up to three digits.Lv<cE4> could become “Lv12”. The value is supplied by the game.
<cE5>Inserts a runtime number using the formatter that allows up to seven digits.A reviewed shop prompt begins <cEC:08><cE5> Gitan. Keep this numeric code and its surrounding spaces.
<cE6>Inserts a runtime number through a separate producer/formatter path, with up to three digits.Used in a reviewed selling-price prompt. It is not interchangeable with <cE4>, even though their digit limits match.
<cF0:XX>
<cF0>		Item descriptions: <cF0:XX> inserts one of thirteen shared text fragments at the current position. Ordinary dialogue: <cF0> is a screen effect, not shared text.In descriptions, <cF0:00> currently inserts “Raises attack.” and <cF0:03> inserts “When equipped:”. Edit these in Shared help text; consumers are remeasured. The ordinary bank-13 message handler also accepts an argument but calls an effect routine. The exact effect mapping is not fully mapped.

The number of characters in a token is not its displayed width. Shared help fragments are measured using their actual text, and known item variants are checked with their suffixes. Other runtime producers may still use a minimum-size estimate; the editor reports that limitation.

Choices, timing and effects

These codes can affect input, drawing, sound or timing without adding visible text. Keep their parameters, order and required leading positions.

CodeWhat is establishedWhat to preserve
<cEC:XX>Banks 11/14 dialogue: a leading prefix used by special windows and choices, including signs, confirmations and road selectors. Default message path: repeats a frame-wait operation using its parameter.A dialogue entry beginning <cEC:08> must keep that prefix first, with 08 unchanged. Its position is part of how the game resumes the entry. Do not interpret all cEC parameters as a dialogue delay.
<cE0:XX>Conditionally calls an effect routine with one parameter; documented as a likely sound trigger. Exact effect/sound mapping not fully mapped.For example, <cE0:2B> appears before a gale announcement. Keep the original parameter and position; changing it is not a wording edit.
<cE1>Calls an effect routine with a fixed value. It does not insert printable text. Visible effect not fully mapped.No parameter follows inside this token. Preserve it where it occurs.
<cE7:XX>
<cE7>		The default message handler stores its parameter in a control flag. Banks 11/14 dialogue use <cE7> without a parameter and set a different flag. Visible behavior not fully mapped.Keep the form used by the entry. On the dialogue path the byte after <cE7> is not a parameter and must not be swallowed into the token.
<mode0>The default message handler clears an engine mode flag. The complete visible meaning of this mode is not fully mapped.Preserve the reviewed effect sequence. This is not a translation-language or editor display setting.
<mode1>The default message handler sets the flag paired with <mode0>. Some reviewed dialogue sequences carry a following raw byte associated with timing. Handler/skip-path interpretation remains unresolved.The current codec writes <mode1> with no parameter inside it. Preserve an existing sequence such as <mode1><$3C> exactly. Do not delete the raw byte or turn the pair into <mode1:3C>.
<cF1>Dialogue-only effect that sets two internal state values. Player-visible purpose not fully mapped.No parameter. Preserve it; it is not an ordinary bank-13 message-path control.
<cF2>Dialogue-only effect that calls a tilemap routine three times. Complete screen effect not fully mapped.No parameter. Keep its place in the effect sequence.
<cF3>Dialogue-only effect that clears an internal flag paired with <cF4>. Visible purpose not fully mapped.No parameter. Preserve the paired sequence as authored.
<cF4>Dialogue-only effect that sets the flag paired with <cF3>. Visible purpose not fully mapped.No parameter. Preserve the paired sequence as authored.

Raw bytes and structural tiles

<$XX> preserves one byte exactly. Its meaning depends on the entry: it may be a tile, padding or part of a reviewed effect sequence. It is not a general way to add a character the font does not support.

CodeKnown useEditing guidance
<$81>The selected-choice cursor in the reviewed choice layouts.In <$81>Yes<br> No, the cursor precedes the first label and the next row retains its leading space. Keep the cursor before its label and preserve the structural spaces. The renderer supplies additional native cursor spacing.
<$B6>A divider tile in the fixed status fields.Those composite rows are references in the website. Their field positions require a renderer change as well as text edits.
<nop>
byte $E9		The native message handler does nothing, but the translated build uses this byte to mark redirected text.Reserved for the build machinery; do not add it to a translation.
byte $FFTerminates a stored string. It is distinct from <end>.The build supplies string termination. Do not insert <$FF> in editor text.

The build also reserves compression codes. Preserve existing raw bytes and use the named token already shown by the entry. A raw byte that encodes successfully is not automatically safe to change.

Opening cinematic

The cinematic editor uses a separate text format. It accepts only <br> and <page>; dialogue substitutions and effects do not apply.

CodeWhat it doesExample or rule
<br>Forces a line break within the current cinematic page.Words also wrap automatically at 152 pixels. Each page must fill exactly the event’s occupied line slots; lines cannot be empty.
<page>Separates the event’s predefined cinematic pages.Look, over there!<page>There's Mount Sasara! illustrates two pages. Keep the event’s page count.

Which rules apply in my editor?

WorkbenchControl and layout rules
ProseOrdinary drafts wrap automatically. You can request <br> and <brk>; the wrapper supplies indents and <end>. Preserve required substitutions, effects and their order.
Choices and structured dialogueKeep explicit breaks, leading controls, cursor positions and structural spaces. Use the entry’s bank-11/14 token forms.
Gameplay messagesPreserve the queued-fragment layout and control sequence. Do not add line or page breaks to a fragment that has none. These messages use the bank-13 forms.
Item descriptionsLine breaks may move within the existing pages. Preserve all other controls and page boundaries. Here <cF0:XX> inserts shared text and uses its full measured space.
Items, names, menus, actions, seals, shared help and conditionsThese are labels, rows or fragments with their own geometry. Preserve any existing controls and structural spaces; do not add dialogue tokens to obtain wrapping or extra room.
Opening cinematicOnly <br> and <page>. Fill the exact line/page slots shown by the event.

Sources and limits

This guide follows the current codec and argument counts, renderer measurements, cinematic layout and project text reference. Older investigation notes contain superseded interpretations.

The editor checks the established text contract. Unknown effect meanings and unmeasured runtime values still need investigation and game testing; a successful text check does not establish their complete behavior.
